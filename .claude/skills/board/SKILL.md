# 경영회의

안건: $ARGUMENTS

이 회의의 목적은 한 안건을 서로 독립된 두 관점으로 분석한 뒤, 적어 둔 원칙으로 결정하고 기록을 남기는 것이다. 순서가 중요하다. 두 담당이 서로의 답을 보고 맞추면 독립된 검토의 의미가 없어지므로 반드시 따로 돌린다.

## 순서

**1. 안건 확인.** 안건이 비어 있거나 어느 사업(이음 / 삼대집)인지 불분명하면 사용자에게 한 번 묻는다. 안건이 "주간 점검"이면 2~3단계를 건너뛰고 `chief-executive`에게 주간 점검을 맡긴 뒤 5단계로 간다.

**2. 독립 분석.** `seo-ux-designer`와 `growth-marketer`를 같은 메시지에서 동시에 실행한다. 각자에게 다음을 전달한다.

- 안건 원문
- 대상 사업
- 사용자가 대화에서 준 추가 정보(수치, 제약, 기한)
- 서로의 결과는 전달하지 않는다

안건이 한쪽 영역에만 해당해도(예: 순수 가격 문제) 둘 다 실행한다. 다른 관점에서 보이는 위험을 잡기 위해서다. 해당 사항이 적은 담당은 짧게 답하면 된다.

**3. 결정.** 두 보고서 전문을 `chief-executive`에게 전달한다. 요약하지 않는다. 요약하면 총괄이 계산을 검증할 수 없다.

**4. 사용자에게 보고.** 총괄의 결정을 중심으로 전한다. 두 담당의 보고는 판정 이유를 이해하는 데 필요한 만큼만 인용하고, 사용자가 원하면 전문을 보여 준다. 세 에이전트의 결론을 당신의 의견으로 바꾸거나 누그러뜨리지 않는다.

**5. 기록.** 총괄이 낸 "결정 로그 기록안"을 `biz/decisions.md`의 "기록" 아래 맨 위에 추가한다. 승인된 실험이 있으면 `biz/experiments.md`의 "진행 중"에 양식대로 추가한다. 총괄이 원칙 수정을 제안했다면 `biz/principles.md`를 바로 고치지 말고 사용자에게 수정 문안을 보여 주고 동의를 받은 뒤 고친다.

**6. 컨텍스트 갱신.** 회의 중 사용자가 새 실측 수치를 줬다면 `biz/context/`의 해당 `[미정]` 칸을 채우고 `[실측]`과 날짜를 붙인다.

## 주의

- 이음 저장소(`../naming`)와 삼대집 저장소가 로컬에 없으면 담당들이 실제 화면을 못 본다. 그 경우 보고 첫머리에 이 한계를 밝힌다.
- 에이전트가 낸 수치 중 `[가정]`인 것을 사용자에게 전할 때 실측처럼 말하지 않는다.
